# Anchor · MV3 平台预研（A1 产出）

> **这篇文档在做什么**：Anchor 是一个 Chrome 扩展，用 Manifest V3（简称 MV3，Chrome 现行的扩展标准）来写。写正式代码之前，我们先把 MV3 平台的几个"硬约束"摸清楚——权限怎么申请、后台逻辑会不会被浏览器随时终止、页面里怎么采集用户行为等。这些结论决定了后面所有模块能不能按预想的方式跑起来。
>
> 对应表单任务：A1（Day 1–2）· 下游依赖：A3（骨架）、A4（采集）、B4（side panel）

## 1. 需要哪些浏览器权限

Chrome 扩展要用某个能力（比如"知道用户切换了 tab"），必须先在 `manifest.json` 里声明权限，用户安装时会看到这些权限列表。下表是 Anchor 每个功能对应要申请的权限：

| 想做到的事 | 需要的权限 | 为什么必须 |
|---|---|---|
| 知道用户切到了哪个网页（域名/标题） | `tabs` + `host_permissions` | 判断"是否偏离锚点"的核心信号 |
| 知道用户是不是离开电脑了 | `idle` | 排除"人走开了"这种误判 |
| 记住状态、缓存、demo 开关，重启也不丢 | `storage` | 见第 2 节：后台逻辑会被随时清空内存 |
| 定时唤醒后台、补一次判断 | `alarms` | 后台的普通计时器（`setInterval`）不可靠，见第 2 节 |
| 判断用户是点链接进来的还是自动推荐进来的 | `webNavigation` | 单页应用（SPA）内部跳转采集不到，见第 5 节 |
| 显示桌宠界面 | `sidePanel` | 侧边栏 UI |
| 在网页里监听键盘/滚动等交互 | `content_scripts` + `host_permissions` | 见第 3 节 |
| 调用 AI 判断相关性 / 生成话术 | 不需要额外权限 | 后台脚本自带 `fetch`，能力直接可用 |

最小 manifest 草案：

```json
{
  "manifest_version": 3,
  "name": "Anchor",
  "version": "0.1.0",
  "permissions": ["tabs", "idle", "storage", "alarms", "webNavigation", "sidePanel"],
  "host_permissions": ["<all_urls>"],
  "background": { "service_worker": "background.js" },
  "side_panel": { "default_path": "sidepanel.html" },
  "content_scripts": [{
    "matches": ["<all_urls>"],
    "js": ["content.js"]
  }]
}
```

## 2. SW 生命周期与状态恢复方案

**后台逻辑会被浏览器随时"杀掉"，怎么办？**

老版本扩展（MV2）有个"background page"，可以一直常驻后台，像个不会停的小程序。MV3 把它换成了 **Service Worker（SW）**——本质上更像一个"按需运行的函数"：

- 大约 **30 秒没有新事件**（用户没切 tab、没有定时器触发、也没有消息传进来），Chrome 就会把这个后台逻辑**直接终止**，内存清空。
- 下次有事件发生，Chrome 才会**重新启动一个全新的实例**，之前存在内存里的变量全部归零，就像重启了一遍程序。

**这会造成什么问题？** Anchor 要靠"计时"判断用户状态，比如"用户多久没碰锚点了""画面静止了多久"。如果这些计时器写成"内存里一直累加的计数器"，一旦后台被终止，计时就断了——等用户安静看了 10 分钟视频（期间没有任何 tab 切换事件），后台早被回收好几次，程序会完全"失忆"，不知道该不该提醒用户。

**Anchor 的解法，三步组合拳：**

1. **只记"绝对时间点"，不记"已经过了多久"。** 比如不维护一个不断加 1 的计数器，而是只存"上次发生这件事是几点几分"（`Date.now()` 时间戳）。要用的时候现算：`经过时长 = 现在时间 - 那个时间戳`。浏览器系统时钟不会因为后台重启而错乱，这个减法永远算得对。
2. **把这些时间戳存进 `chrome.storage.local`**（浏览器自带的本机小型数据库，进程重启、电脑重启都不会丢）。后台每次重新启动时，第一件事就是把这些数据读回来，"复原"出应有的状态，而不是从零开始。
3. **用 `chrome.alarms` 定一个 1 分钟一次的心跳闹钟。** 普通的 `setInterval` 会跟着后台一起被杀死、失效，但 `chrome.alarms` 是浏览器平台层面调度的，闹钟响的时候**保证**会把后台唤醒。这样即使用户完全不操作，最多 1 分钟后台也会被叫醒一次，重新读取存档、补算一次最新状态。

**恢复时序**：后台启动 → 从 `chrome.storage.local` 读出上次存的状态（`BStatePersistable`）→ 用当前时间和存档里的时间戳重新算出"脱离锚点多久了"之类的指标 → 继续正常判断。

**一个诚实的已知限制**：不是所有状态都能这样救回来。有一类"持续证据"计时器（`sustainer.since`）没有做持久化——因为后台被回收这件事本身就意味着中间那段时间完全没有数据，硬要伪造一个"连续"的计时反而不可靠。所以后台醒来后，这类计时器会**从当前这一刻重新开始计**，最多导致用户被提醒的时机晚个 30 秒左右。这是权衡后的取舍，不是 bug。

## 3. 网页里怎么采集用户行为

- Anchor 需要在**所有网页**里监听键盘、滚动等动作，所以用最简单的"静态注入"方式（在 manifest 里声明 `content_scripts`，浏览器自动帮你插进每个页面），不需要更复杂的按需注入。
- 对视频网站（YouTube、B 站等）还要额外监听播放/暂停/跳转。难点在于：这类网站是"单页应用"，切换视频时页面不会整个刷新，视频播放器元素可能被悄悄替换掉，监听器会失效——需要用 `MutationObserver`（监听 DOM 变化）定期重新绑定，这是后续实现时要注意的风险点。
- 网页里的脚本和后台之间靠 `chrome.runtime.sendMessage` 传消息。

## 4. 各部分之间怎么通信

```
网页里的脚本 --(发消息)--> 后台 --(写入本地存储)--> 侧边栏界面
                              ↕ 发消息（触发提醒 / 用户回答）
```

- 侧边栏打开着的时候：直接用消息双向通信，最简单。
- 侧边栏关着的时候：后台把"要不要提醒用户"的判断结果先写进本地存储，等用户重新打开侧边栏时，侧边栏读取存储、并订阅存储变化事件，把结果显示出来。

## 5. "用户是怎么进到这个网页的"能不能采到

- 浏览器提供了一个事件，能告诉你用户是点了链接、还是自己在地址栏打字进来的——但这只对**整页跳转**有效。
- 像 YouTube 自动播放下一个推荐视频这种情况，页面并没有真正刷新，触发的是另一个事件，**拿不到"怎么进来的"这个信息**，只能靠"猜"：如果域名没变、只是网址变了，大概率是自动推荐播放的。
- 所以这个信号只能当"参考"用来加速判断，不能作为主要证据——万一猜错了代价太大。

## 6. 用什么工具打包扩展

- 用 **Vite + CRXJS 插件** 打包，这是目前 MV3 扩展开发的主流组合，改代码后能热更新，侧边栏的 React 界面也能接入同一套构建流程。
- 项目的纯逻辑部分（不碰任何浏览器 API 的那两块引擎代码）单独用 vitest 测试，跟扩展打包互不干扰——保持"纯逻辑不依赖浏览器"，方便脱离扩展环境单独验证正确性。

## 7. Demo 模式开关

- 往本地存储里写一个 `anchor_demo_mode` 标记位，后台启动时读取。开启后，所有等待时长会被大幅压缩，方便演示时不用真的等 8 分钟、20 分钟。
